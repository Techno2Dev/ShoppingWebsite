# Sapana’s Kitchen Katta

A small full-stack storefront starter: Angular 8 frontend and ASP.NET Core 9 API, with PostgreSQL (EF Core, Neon-compatible) or MongoDB persistence.

## Prerequisites

- .NET 9 SDK
- Node.js and npm
- A PostgreSQL database, such as Neon, or a MongoDB replica set / sharded cluster

## Run locally

1. Create a PostgreSQL database (for example Neon) or a transaction-capable MongoDB database. Set its connection URI as `ConnectionStrings__Store` for the API. Neon `postgresql://` URLs are converted for Npgsql automatically; MongoDB URIs require a database path. For local development, keep the URI in user secrets or your shell environment; do not commit credentials.
2. From the repository root, start the API with `cd .\backend` followed by `dotnet run --launch-profile http`. It listens at `http://localhost:5065`.
3. In a second terminal, install frontend dependencies if needed with `npm --prefix .\frontend install`, then start Angular with `npm --prefix .\frontend start`. Open `http://localhost:4200`.

On first start, EF Core creates the PostgreSQL tables and adds sample products if the product table is empty. Products, uploaded product-image bytes, orders, order items, payment status, and admin accounts are stored in Neon. The image upload accepts JPG, PNG, GIF, and WebP up to 5 MB. The existing local SQLite database is not copied to Neon automatically; export/import any data you need to retain before switching.

### MongoDB instead of PostgreSQL

Set `ConnectionStrings__Store` to a `mongodb://` or `mongodb+srv://` connection URI **including the database name as its path**, for example `mongodb+srv://USER:PASSWORD@HOST/store?retryWrites=true&w=majority`. Put the real URI in an environment secret, not in source control. The API automatically selects its MongoDB-driver-backed controllers; PostgreSQL's EF Core controllers, SQL setup, and existing PostgreSQL behavior remain unchanged for non-MongoDB connection strings. MongoDB uses its own collections and does **not** read or automatically import existing PostgreSQL/SQLite records. Plan a separate migration and backup if you need existing data when switching backends.

MongoDB must be a **replica set or sharded cluster with transaction support** (including Atlas); standalone `mongod` is rejected at startup. The database user needs permission to create collections and indexes, read/write transactions, and run `hello`. On first start the API creates uniqueness, lookup and session-expiry indexes, provisions the configured administrator and seeds six products when empty. Order creation, stock reservation, cancellation/restock, payment review/restock, administrator credential rotation, and customer sign-in/session issuance use MongoDB transactions. Prices and totals are stored as BSON Decimal128; uploaded images remain in product documents (uploads are limited to 5 MB). For a local MongoDB instance, configure a single-node replica set rather than running standalone. Do not use a MongoDB deployment lacking transactions; the application will not fall back to non-atomic writes.

The admin dashboard requires sign-in. In Development only, the demo account is `admin` / `KitchenKatta@123`. In Production, provision the first administrator by setting `Admin__UserName` and `Admin__Password` in the service environment before first start. The password is stored as a salted PBKDF2 hash. Keep database and admin credentials in environment secrets, not source control.

New guest and signed-in checkouts require a 10-digit Indian mobile number for delivery contact. Signed-in customers may optionally save one in My Details to prefill checkout; it is also supplied as the contact for Razorpay test checkout. Admins can see and tap the number in order details. Orders created before this change keep a blank number; deployment adds nullable database columns without altering old records. Deploy the API and frontend together so the checkout field and server validation agree.

### Optional Google customer sign-in

Create an OAuth **Web application** client in Google Cloud Console, configure the consent screen, and add your actual frontend origins to **Authorized JavaScript origins** (for example `http://localhost:4200` and your HTTPS Render frontend origin). Set its **client ID** as `Google__ClientId` on the backend (or in a Git-ignored local settings file when running in Development); no Google client secret is needed for this ID-token flow. Restart the backend and redeploy both services. The backend verifies Google's ID-token signature, issuer, audience and expiration and checks that the email is verified before issuing a seven-day customer session. Customer and admin sessions use separate authorization policies. Customer session tokens are kept in tab-scoped browser storage; use HTTPS for deployed services. The header shows **Login → Continue with Google**, then a profile photo/menu with separate **My Orders** and **My Details** pages. Only orders placed while signed in appear in My Orders. Guest checkout and private order-resume tokens continue to work without Google; a previously created guest order can be linked from its current tab only by presenting that order's original private token—matching an email alone never links orders. Customer names and delivery addresses can be saved; Google supplies the profile email and photo. Admins can advance **paid** orders from Order received → Dispatched (requires tracking ID) → Delivered in the order-details view; payment status is independent of delivery status.

Prices are in Indian rupees (INR). The Angular app uses the supplied Sapana’s Kitchen Katta logo and keeps the cart in browser local storage. To enable UPI QR checkout, configure `upiVpa` and `upiPayeeName` in the frontend environment files. Each order reserves stock and gives the customer a private, tab-scoped payment-resume token. Customers can reopen the QR after navigation or refresh, copy the UPI ID, and must enter a UPI transaction/UTR reference (6–100 characters) to report payment. Payment status stays **Pending** when a customer reports the UTR; only an admin can change it to Paid or Failed. Customers who have **not sent money or reported a UTR** can cancel their Pending order from the QR screen: this marks the order **Cancelled**, releases its reserved stock once, and cannot be undone. If money was sent, customers should report the UTR or contact the store; cancelling an order does not initiate a refund. Admins compare the report/reference with the bank statement before marking an order Paid or Failed; the app records the reviewer and review timestamp. Manual UPI orders have no payment timeout and keep their reserved stock until an admin changes the status or the customer explicitly cancels an unpaid, unreported order. The UPI QR option has no automatic bank verification.

### Razorpay test payments (optional)

For **local testing**, fill in the `Razorpay:KeyId` and `Razorpay:KeySecret` fields in `backend/appsettings.Local.json` with your Razorpay **test** keys. This file is ignored by Git, excluded from Docker and published output, and loaded only when the backend is running in Development. Do not paste keys into `backend/appsettings.json`. Start the backend with the `http` launch profile and restart it after changing keys. The development Angular environment already points to `http://localhost:5065/api`; the production environment still points to Render. You may leave `WebhookSecret` empty for local testing and refresh customer payment status to reconcile a captured payment; receiving webhooks locally requires a public tunnel and a matching secret. Environment variables take precedence over the local file.

The cart offers **UPI QR** (unchanged, manually verified) and **Razorpay test checkout** (automatically verified). Create Razorpay **Test Mode** API keys and configure `Razorpay__KeyId` (`rzp_test_...`) and `Razorpay__KeySecret` as **backend** environment secrets. The gateway option is disabled when these are absent. Never put the secret in Angular or commit it. Deploy the API before the frontend; use the same test account for keys and webhook. Set up a Razorpay Test Mode webhook for `payment.captured` pointing to `https://YOUR-API-HOST/api/razorpay/webhook` and set its separately generated signing secret as `Razorpay__WebhookSecret`. Enable automatic payment capture in the Razorpay dashboard. Razorpay test payments do not charge real money. The server creates a Razorpay order for the stored INR total, checks the checkout signature using the server-side key secret and checks **captured** status, gateway order ID, amount and currency with Razorpay's API before marking Paid. The webhook is signature-checked and idempotent; customer status refresh can reconcile captured payments if the browser closes before the callback. A failed/closed checkout remains Pending; Razorpay orders are not eligible for UPI UTR reporting or manual Paid/Failed changes. After checkout starts, online cancellation is disabled because a payment may still be in flight. Refunds must be handled separately in Razorpay, not through the existing manual UPI refund status. This integration deliberately rejects live keys; do not use it for production charges without implementing and testing a full live-payment/refund process.

### Optional Telegram order alerts

Create a Telegram bot through BotFather, open a private conversation with the bot and send it a message (for example `/start`). Obtain that conversation's numeric chat ID from Telegram's Bot API `getUpdates` response; for a group, add the bot to the group and use the group's chat ID instead. Set `Telegram__BotToken` and `Telegram__ChatId` as **backend Render service environment secrets**, then redeploy the API. Never add the token to the Angular environment or source control. The API sends a short alert when an order is committed and another when the customer submits a UTR. Alerts contain the order number and (for new orders) amount, but no customer address or order access token. Both events remain **Pending** until an admin checks actual receipt in the bank/UPI account; Telegram does not verify payments. If Telegram is unavailable or not configured, checkout/reporting still succeeds; notification delivery is best-effort and is not retried.

## Admin sign-in

For local development, the API creates a demo administrator if one does not already exist:

- Username: `admin`
- Password: `KitchenKatta@123`

Admin sign-in returns a random eight-hour bearer token. The browser keeps it in tab-scoped session storage and sends it in the Authorization header for admin requests, so deployed admin access does not rely on third-party cookies (including in InPrivate mode). Only its SHA-256 hash is stored in the selected database's admin-session table/collection; logout revokes it. Protect the frontend from injected scripts, since JavaScript in the same origin can access tab storage. The API must allow the exact frontend origin through CORS. To change credentials, sign in to Admin, select **Change login**, enter the current password, then set a username (3–100 characters, no spaces) and a new password (at least 12 characters). Changing credentials revokes other admin sessions and issues a new token for this tab. The administrator record is stored in the selected database; passwords are hashed using PBKDF2-SHA256 with a unique random salt, never stored in plaintext. The demo account is seeded only in Development. In Production, set `Admin__UserName` and `Admin__Password` before first startup to provision the initial administrator; change the demo credentials before deployment.

### Festival greetings on the storefront

Edit [frontend/src/app/festival-schedule.ts](frontend/src/app/festival-schedule.ts) to maintain the welcome card greetings. Each entry specifies a start and end day (inclusive), label, heading, message, and decorative motif. Use `MM-DD` for fixed annual celebrations; use `YYYY-MM-DD` for moving festivals and update those dates every year after checking an authoritative calendar. A dated Diwali 2026 greeting is included; it will **not** recur on the same dates in later years. The browser evaluates the schedule in India Standard Time on load, every minute, and when the tab becomes visible. Outside scheduled dates the existing featured-product card remains unchanged. Update and redeploy the frontend after changing the schedule; it is bundled at build time and cannot be edited through the admin dashboard.

## Build

Run `dotnet build .\backend\backend.csproj` and `npm --prefix .\frontend run build` from the repository root. The frontend build explicitly selects Angular's production configuration, replacing `frontend/src/environments/environment.ts` with `frontend/src/environments/environment.prod.ts`. `npm --prefix .\frontend start` continues to use the development environment. The backend's HTTP profile is configured in `backend/Properties/launchSettings.json`; update the frontend API URL in `frontend/src/environments/` if you change that port.

## Deploy the API on Render

Create a Render Web Service from this repository using the Docker runtime. Set the service root directory to `backend` so Render uses `backend/Dockerfile`. Configure these environment variables in Render: `ConnectionStrings__Store` with the Neon connection string, `Admin__UserName`, and `Admin__Password`. The API CORS policy allows the current frontend `https://shoppingwebsite-1-9ytf.onrender.com`; override it with `FrontendOrigin` (or comma-separated `FrontendOrigins`) if the frontend domain changes. The container binds to Render's `PORT` (default 10000). Deploy the Angular app separately as a Static Site from the `frontend` directory, with build command `npm install && npm run build` and publish directory `dist/frontend`. Set the API URL in `frontend/src/environments/environment.prod.ts` to the deployed API URL ending in `/api` before building the Static Site. Redeploy the frontend after changing a build-time environment file; a Static Site does not read it at runtime.
